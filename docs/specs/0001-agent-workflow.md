- 范围：仓库治理、架构文档、评审记录、开发检查与 CI；不改变产品运行行为。

## 问题与目标

仓库已有产品 SPEC 与三层实现，但缺少 Agent 入口、逐项变更规格、明确的确认门槛和自动化架构检查。建立从需求到验收的闭环，让后续 Agent 能知道哪些是事实、哪些是目标、哪些尚未批准。

## 范围与非目标

本次提供根目录 `AGENTS.md`、当前架构、标准开发流程、变更 spec 模板与索引、评审报告、PR 模板、架构检查及 CI。产品定位继续沿用 `docs/SPEC.md`。

不在本次修复 raw 版本覆盖、调整 MCP 工具行为、迁移 SQLite、替换 SDK、接入真实平台或部署。评审发现的问题登记并进入后续 spec。

## 设计与契约

1. Agent 开工读取根规则、产品 SPEC、架构及本次变更 spec。
2. 后续功能、修复、重构、依赖及数据契约变更必须先有 spec；负责人确认后才改实现。已有明确授权可引用，不重复索要确认。
3. spec 状态为 `draft → approved → implementing → done`；`superseded` 表示被替代。没有确认依据不能从 draft 前进。
4. 当前实现与目标约束分别记录。为既有架构债务设精确例外，禁止用宽泛豁免掩盖新增违规。
5. 自动检查覆盖静态导入边界；负责人确认属于人工门槛，CI 不声称能够证明它。
6. 验证仅使用临时 DB、local raw、fixture 和 HTTP mock；不触碰真实数据。

## 验收标准

- AC-1：根 `AGENTS.md` 能指导后续 Agent 完成读取、spec 确认、实施、验证和交接。
- AC-2：架构文档包含实际依赖方向、公共契约、已知例外和后续演进门槛。
- AC-3：变更模板包含范围、非目标、接口、失败语义、验收、验证、迁移/回滚及确认记录。
- AC-4：架构检查对当前代码通过，并有负例证明跨层违规会失败；相对导入同样受检。
- AC-5：CI 执行架构检查、单元测试和离线 L0 smoke；基线失败如实记录，不能通过跳过、吞错或减弱断言伪装通过。
- AC-6：整体评审按优先级列出可定位的证据、验证结果和建议次序；产品修复 spec 先以 draft 交付，仅在真实确认后进入实施。
