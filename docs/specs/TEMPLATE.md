# SPEC-NNNN：变更名称

- 状态：draft
- 日期：YYYY-MM-DD（Asia/Shanghai）
- 需求来源：用户请求 / issue / 评审问题编号
- 关联：产品 SPEC 章节、前序 spec、架构决定

## 问题与证据

触发条件、当前可观察行为、期望结果、代码定位或隔离复现。推断与已验证事实分开。

## 目标与非目标

列出本次必须交付的行为、明确排除的扩展和受影响模块。

## 方案与架构

数据流、允许的依赖方向、复用扩展点、备选方案与取舍。局部变更可简写；新增模块/依赖必须说明理由。

## 契约与失败语义

输入/输出示例、参数边界、身份与源 URL、时间/时区、provenance、状态、幂等、部分成功、重试与错误记录；不适用项说明原因。

## 数据、兼容、迁移与回滚

旧 DB/raw/环境变量/调用方如何兼容；迁移如何验证；失败如何恢复；回滚是否涉及不可逆写入。没有数据影响时明确写出。

## 验收标准

- AC-1：Given … When … Then …（外部可观察、可验证）。
- AC-2：边界/失败情况下 …。

## 验证计划

| AC | 方法/命令 | 通过条件 |
|---|---|---|
| AC-1 | 测试或人工检查 | 具体结果 |
| AC-2 | 故障注入/边界测试 | 具体结果 |

使用隔离 DB/raw、fixture/mock。列明真实环境验证的必要性与已有授权；未运行的检查不能记作通过。

## 实施计划

按契约/数据 → 业务实现 → 入口适配 → 验证/文档划分最小步骤；每步对应验收，不必预先列每一行代码。

## 未决问题

标明阻塞实施的产品/架构决策和非阻塞细节；没有则写“无”。

## 确认记录

待确认。记录负责人、时间、会话/PR 证据与被确认版本/范围。Agent 不能自行确认。已有明确授权可引用，不重复询问；需求扩大仅确认增量。

## 交付与验证记录

实施后填写实际变更、命令/环境/版本、AC 结果、未解决限制；全部验收完成才改为 done。
